## 1 为什么需要

`pmset` 电池档 `displaysleep=2`（本机实测）：构建几分钟后显示器已睡 ⇒
`requestActivate()` 再也拿不到焦点 ⇒ `QGuiApplication::focusObject()` 恒 `nullptr`。

旧行为（T29 定案）：

```
IT-06 仪器不可用：窗口 N 次 requestActivate 后仍未获得系统焦点（isActive=false）
   ⇒ uiInteractFinish(...)          // ← 整个套件立即收尾
   ⇒ 判据 5/6                        // ← 后面 9 条**根本不存在**
   ⇒ exit(10)
```

两个毛病：

1. **报告残缺** —— 套件声称有 16 条判据，实际只跑出 5~6 条，且看不出"缺的是哪几条"；
2. **语义错位** —— `rc=10` 的约定是"**FAIL**"，读日志的人会去追**产品缺陷**；而这里的
   事实是"**仪器测不到**"。T29 当时只能这么记，因为套件还没有第三态。

## 2 语义设计：引入第三种结果 UNAVAILABLE

与 PASS / FAIL 并列：

| 结果 | 含义 | 退出码 |
|---|---|---|
| PASS | 判据被执行且成立 | 0 |
| FAIL | 判据被执行且**不成立**（产品/布场真有东西坏了） | 10 |
| **UNAVAILABLE** | **判据的前提不成立 ⇒ 根本没被执行** | **6** |

三条规矩：

- **不是 FAIL**：记 FAIL 会让人去查一个不存在的产品缺陷；
- **不是 PASS**：判据**未被验证** —— T29 的"**不洗成 PASS**"原则照旧成立；
- **退出码优先级 = FAIL(10) > UNAVAILABLE(6) > PASS(0)**：真有东西坏了永远优先报。

报告形如：

```
INTERACTCHECK: 判据 12/12（另 5 条 UNAVAILABLE：IT-06,IT-13,IT-14,IT-15,IT-16）
INTERACTCHECK: VERDICT=UNAVAILABLE
```

## 3 分类依据：**探针实测**（以及一次被"级联假红"骗过）

门失败时**哪些判据算不可判**，不能靠推理。本轮为此专门做了**失活探针**：

```
STELQUICK_INTERACT_FORCE_INACTIVE=1    # 置 Qt::WindowDoesNotAcceptFocus（窗口仍可见/仍渲染）
STELQUICK_INTERACT_PROBE_ACTIVATION=1  # 门失败后**照跑**（不置标志、不跳任何判据）
```

两者一起用 ⇒ 在"真实失活"的窗口上把 16 条判据**全跑一遍**，读数就是边界。

**这条弯路值得留档**：

| 轮次 | 结论 | 依据 | 判决 |
|---|---|---|---|
| ① 推理 | IT-07..12 **不依赖** | 鼠标走 `sendEvent` 直达窗口 ⇒ `deliverPointerEvent` 不查 `isActive` | ✅ 最终正确 |
| ② 负控首跑 | IT-07..12 **依赖** | 窗口偶然失活时 IT-07/08/09 **全红** | ❌ **被级联骗了** |
| ③ 探针实测 | IT-07..12 **不依赖** | 强制失活 + 照跑 ⇒ IT-07..12 **全绿** | ✅ 定案 |

② 的红是**级联**：门失败后我把 **case 8 整个 `break`** 掉 —— 连它末尾那句
"**切回天空页**"（IT-07 的舞台）也没执行 ⇒ IT-07 在**搜索页**上拖拽 ⇒ 红的是**布场**，
不是依赖关系。**教训**（血泪第 4 条的又一实例）：一个判据红，先问"**它的前提成立了没有**"，
再谈"它测的那个东西坏了没有"。

**为什么 IT-15 / IT-16 明明是绿的也算依赖**：

- **IT-15** 的前提（`imeTextBefore` = "组合前的正文"）由 IT-13 建立。失活时点击搜索框
  **给不了焦点** ⇒ preedit 没进输入框 ⇒ 基线是**空串** ⇒ commit 进来刚好等于
  `"" + "月球"` ⇒ **通过**。成对腿（"正文不该被 preedit 污染"）**根本没成立** ⇒ 这是
  **偶然通过**，不是验证。
- **IT-16** 是 IT-14 的**判别性对照**（同一个键、同一个页，只差焦点位置）。对照的另一半
  不可判时，它单独绿**说明不了"修复没把返回链路一起杀掉"** —— 血泪第 20 条：
  "**否定式判据单独绿没有意义**"。

⇒ macOS 上量到的边界（`kFocusGatedIds` 的一个**子集**）：

```
IT-06, IT-13, IT-14, IT-15, IT-16
```

### 3.1 🔴 补充实测（W-T31）：**边界是平台相关的，表要取并集**

同一份代码拿到 Windows（原生 Vulkan）上再跑一次探针，读数**不一样**：

| 平台 | 探针读数 | 失活下**红**的（⇒ 激活依赖） |
|---|---|---|
| macOS（Metal） | `判据 13/16` | IT-06 焦点守卫、IT-13/14 IME |
| Windows（原生 Vulkan） | `判据 12/16` | **IT-05 键**、IT-06、IT-13、**IT-16**（靠键的 Esc 对照） |

**IT-05 在 Windows 上是激活依赖的，在 macOS 上不是。** 原因就是 T29-W 那条老坑：
Windows 窗口未激活时 `forceActiveFocus()` 拿不到 active focus ⇒ 注入的键
**根本进不了 `keySink`**（实测读数 `dispatched=0`、`lastActionId=""`）；
macOS 的 `activeFocusItem` 在失活时仍被设置，所以键照样到。IT-16（Esc 对照）同理
——它靠的也是键。

⇒ **出厂表 = 两平台并集**：

```
IT-05, IT-06, IT-13, IT-14, IT-15, IT-16
```

取舍原则：**少判一条只是覆盖率损失；把"仪器测不到"报成 FAIL 才是语义错误**
（那正是本任务要消灭的东西）。

⚠️ **这个并集反过来决定了门的位置**：IT-05 在相位 6，而原来的门在相位 7（IT-06）
⇒ 若只把门放在相位 7，**IT-05 会以 FAIL 的形式漏出去**。细节与修法见 **§4.1 ②**。

## 4 实现：**相位编号一处未动**

这是当初把它"留待后续"的顾虑 —— 套件相位编号被多个任务共用，跳号的风险 > 收益。

现在的做法**完全不动编号**：

- 门失败 ⇒ `uiInteractEnterFocusUnavailable()` **置标志** `focusGateFailed` + 记**当前**
  判据的 UNAVAILABLE，然后 `break` **正常推进相位**（不再 `exit`）；
- 每个**激活依赖**判据的相位开头：

  ```cpp
  if (c->focusGateFailed)
  {
      uiInteractUnavailable(c.get(), "IT-xx", c->focusGateWhy);
      break;                       // 只跳判据/写入步，相位号照常 +1
  }
  ```

- ⚠️ **写入步（布场）与判据要分开对待**：case 8 那句"切回天空页"是 IT-07 的舞台 ⇒
  门失败时**判据跳过、写入步照做**（就是 §3 表 ② 行的那个坑）。

### 4.1 两条实现纪律

**① 置标志 ≠ 记账：记账必须"恰好一次"。**

UNAVAILABLE 的行由**各判据自己的相位开头**记；但标志可能由**更早的相位**置上
（前导激活门超时、IT-06 相位自己那轮门失败）。于是拆成两个 helper：

```cpp
uiInteractSetFocusGateFailed(c, why)     // 只置标志，不记账  ← 早于该判据的相位用
uiInteractEnterFocusUnavailable(c, id, why)  // 置标志 + 记一条 ← 由该判据自己的相位调
```

**重复记账**会让收尾的"跳过集合 == 分类表后缀"自检**假红**（跳过的 ID 出现两次，
与表的后缀集合对不上）—— 一个纯粹由**仪器自己**造出来的红，和产品毫无关系。
§3.1 的并集修正（前导门**必须**在 IT-05 之前置标志）把这条从"理论风险"变成了**必须显式处理**。

**② 门的位置 = 表里第一条依赖判据之前。**

第二版把分类表扩到含 **IT-05**（相位 6）之后，若门仍只放在相位 7（IT-06），
**IT-05 会以 FAIL 的形式漏出去**（Windows 首轮就是这个形态：
`✗ IT-05 天空页注入 L 键 → timeRate 0.1 → 0.1（应变），dispatched 累计=0`）。

⇒ 前导门（相位 0）**超时时必须自己置标志**（用上面的 `Set` 版本，不记账）。
换句话说：**分类表的成员位置反过来决定了门要放在哪** —— 改表时不能只看表，还要看门的相位。

**唯一新增判据** `INTERACT-INTEGRITY`（收尾，纯逻辑腿）：门失败时校验

```
实际被跳过的 ID 序列  ==  分类表里"从失败点起的后缀"
```

- **漏跳**（有激活依赖判据在错误前提下跑了）⇒ 红；
- **多跳**（把能跑的判据也丢了）⇒ 红。

值来自两条**独立**路径（各相位实际记录 vs 常量表）⇒ 不是复述同一个事实（血泪第 4 条）。
只在"**门失败 ∧ 到此刻零 FAIL**"时执行：套件若中途因**真前提失败**（如"捏合判据需要
天空页"）提前收尾，被跳过的后缀本就不完整 —— 那是套件崩了（rc 走 10），不是降级有缺陷。

**只降级"环境门"**："切页后页码不对""视线基线无效"这类**真前提失败**仍旧立即 `exit(10)`。

## 5 四个开关（都在仪器里，产品代码零改动）

| 开关 | 作用 | 用途 |
|---|---|---|
| `STELQUICK_INTERACT_FORCE_FOCUSGATE_FAIL=1` | 相位 7 入口**强制**置降级标志 | **负控**：验证降级逻辑本体（不必真把显示器睡掉） |
| `STELQUICK_INTERACT_FORCE_INACTIVE=1` | 置 `Qt::WindowDoesNotAcceptFocus` | **探针**：造真实失活环境 |
| `STELQUICK_INTERACT_PROBE_ACTIVATION=1` | 门失败后**照跑**（不置标志） | **探针**：测量各判据的激活依赖边界 |
| `STELQUICK_INTERACT_REQUEST_ACTIVATE=1` | 入口排 3 次 `requestActivate()`（0.15/0.40/0.90s） | **前台提升**：解决"从非前台进程启动的 app 拿不到焦点"（见下） |

`FORCE_FOCUSGATE_FAIL` 走的是**与真实门失败同一个置标志点**
（`uiInteractEnterFocusUnavailable`）⇒ 负控验证的就是那一句之后的全部控制流；
"重试循环"本身是既有代码（T27/T29 已有实测日志）。

**第四个开关是本轮被迫做出来的仪器**（附一条被推翻的旧结论）：

正题读数是"在**真实前台**环境下 16/16"，而套件是由脚本**直接 `exec`** 启动二进制的
—— 这种进程拿不到系统焦点，且会被 macOS **App Nap 节流**（实测事件链整段退化：
滚轮 IT-02/03 不动、RETURNUI 的 RT-08"+1 时"点击不生效；**这两条都不是 T31 引入的缺陷**）。

第一版办法是外部 `open -a <bundle>` 把已运行实例带到前台。**两轮实测推翻**：

| 轮次 | 做法 | 结果 |
|---|---|---|
| 第 2 轮 | 启动脚本 `sleep 1.5` 后 `open -a` | 正题 5/5 `16/16` —— 看起来成了 |
| 第 3 轮 | 同上 | 正题 **5/5 `env-skip`**，日志里前导激活门 3 次 `requestActivate` 全失败 |

根因两条，**独立**且都致命：

1. **幽灵实例** —— 脚本 `exec` 直启的进程**不被 LaunchServices 认作 `.app` 的实例**
   ⇒ `open` 会**另起一个实例**（`pgrep` 见两个 pid），前台给的是幽灵，要等的那个
   依旧 `isActive()==false`；
2. **时序** —— 外部 `sleep 1.5` 才 `open`，而前导激活门的窗口只有
   `3 × 400ms = 1.2s` ⇒ 门**早已超时**。

**改法**：让 **app 自己抢前台**（进程内自激活），0.15/0.40/0.90s 三次，
盖住"窗口刚上屏 / 启动瞬间被别的进程抢走前台"的窗口期。实测**首跑即
`判据 16/16`、门"重试 0 次"**，全量 5/5。

⚠️ 该 env **只在置位时有作用**：不设它就不排定时器、不打任何新行 ⇒
**正题判据行与 T29/T30 逐字不变**（负控/探针也**刻意不设** —— 它们要造的就是失活）。
