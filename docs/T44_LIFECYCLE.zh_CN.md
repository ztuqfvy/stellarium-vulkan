## 2. 方法：为什么用替身生产者

### 2.1 引擎形态物理上不可行

引擎形态单次启动的**真实预热是 ~900 秒**（T9 实测，见 `BUILD_RECORD`）。
P-LIF-01 要求 ×100 ⇒ 100 × 900s ≈ **25 小时**，还只是预热，不含测量。
这条不是"性能问题"，是**不可行**。

### 2.2 生命周期验什么，不验什么

生命周期验的是 **帧通路与窗口/场景图资源的寿命**，与"帧从哪来"无关
⇒ 用替身生产者 `LiveFrameSource`（独立线程 + kOwn 离屏上下文）是正确取舍。

**产品代码路径零改动**：`FrameMailbox`、`SkyViewport`、上传、上屏全是真的。
被替换的只有"帧的产出者"。

> ⚠️ **诚实性声明（必须与结论一起读）**：本组判据**不覆盖**引擎 GL 资源在窗口
> 生命周期上的释放。那一面由 T9/T13 的**进程级长跑**间接覆盖（进程退出即拆引擎）。
> 本组判据给出的结论严格限定为：
> **「在给定帧率与尺寸下，窗口/场景图/邮箱在 100 轮生命周期事件下不崩、不死锁、
> 不无界增长、恢复后帧号重新推进」** —— 不含"引擎纹理无泄漏"。

### 2.3 观测面（全部走公开面）

| 面 | 读法 | 为什么不能更细 |
|---|---|---|
| `skyViewport` | `objectName` 找 `QQuickItem*`，泛型 `property()` 读 `displayedFrameNumber` / `viewportGeneration` / `uploadCount` / `ready` | `src/app` 与 `src/ui` 的检查一律**不依赖具体类型**，避免层依赖倒过来（T33/T41 教训） |
| `FrameMailbox::Stats` | `published` / `dropped` / `completeSlots`（= 队列长度）/ `latestFrameAgeMs` / `sizeGeneration` | 都是公开只读字段 |
| `QWindow` | `isVisible` / `isExposed` / `geometry` / `windowState` | — |

### 3.2 🔴 最贵的一课：`delayAfter` 时序缺陷（陷阱 102，T44-C 才暴露）

上面 §3 表里 **Q2 / Q6 / Q7 三条的原始读数，时间窗全是错的**，而探针直到 T44-C
写判据时才暴露。机制（陷阱 102 全文见 `TRAPS.md`）：

- 步进结构里 `delayAfter` 的语义是"跑完**本步**之后等"（陷阱 41）。于是
  `Step{0, 动作}` → `Step{N, 采样}` 里的采样**在动作之后 0ms 就执行**，
  那 N ms 等在了**采样之后**。
- 探针侧后果：Q2/Q7 标着「最小化 1.2s 期间」，实际量的是**最小化之前**的 900ms；
  Q6a 的交替序列被误定性为"采样相位伪影"，真因是三个动作**同瞬发出互相竞速**。
- 判据侧后果（更贵）：`LIFECHECK` 第一版同款结构 ⇒ LF-03 全程 `世代 X→X` /
  `帧号 +0` / `投递 +0`，而 host 侧 `hostPub +360`、`leased +356`、"帧龄 3ms"
  —— **四组读数互相"矛盾"**，烧了 6 轮仪器迭代去查"对象身份分裂/计数重置"，
  全是白烧。根因只有一个：**采样读的是"0ms 后的世界"，却当成"260ms 后的世界"在解释。**
- 治法：**字段改名 `waitBefore`（跑本步之前等）**。语义反转后
  "动作 → 等 S → 采样"在代码里就是三步相邻有序，这类错误**在语法上不可能重犯**。
- 两个信号提醒你踩了这条：① 同一个量"轮内恒定、跨期递增"；
  ② 动作的效果在**下一轮**的快照里才看得见。
- **别给错误的读数编一个自洽的理论** —— 先验证读数的时间窗是不是你以为的那个窗。

### 6.5 连带修复（本轮顺带抓到的真缺陷）

1. 🔴 `ErrorCheck` EC-16 用 `QLatin1String("配置文件")` 做比较 —— `QLatin1String` 按
   Latin-1 解读 `const char*`，"配置文件"是 UTF-8 字节 ⇒ 与 `QStringLiteral` 生成的
   QString **永不相等**，行明明在却报"无此行"。全仓扫描仅此一处，已改 `QStringLiteral`，
   `ERRORCHECK` 复验 `rc=0 / VERDICT=PASS`（EC-16 `state=ok text「正常」`）。
   （EC-04/EC-11 只数行数所以此前没暴露 —— **判据若只数行数，字符串比较的错它看不见**。）
2. 🔴 `tools/*.sh` 里 `$VAR` 后面**直接跟全角标点**（28 处，如 `×$RUNS（`、`$CAFFEINATE_PID，`）
   —— 在 `LANG=C` 的执行环境里，bash/zsh 会把全角字符的首字节并进变量名
   ⇒ `CAFFEINATE_PID<0xEF>: unbound variable`，脚本当场死。
   已批量改为 `${VAR}`（只在"后直接跟多字节字符"时改，零误伤）。
3. 🔴 `a6-verify.sh` 的负控枚举：`A6_T44_NEGCTL` 已设却解析失败（如用 `bash` 跑这个

## 7. 结论与移交

**T44 结论**：P-LIF-01..04 四条生命周期判据全部落地并全绿——

- P-LIF-01（进程级关闭/重开 ×20 冒烟，收口 ×100 用 `A6_LIF_N=100`）：无崩溃、无死锁，
  首帧每轮都上屏（median 1131ms），config 零污染。
- P-LIF-02/03/04（进程内 ×100 ×3 组）：判据 13/13；帧队列有界且不积压、世代逐次递增
  且单调、恢复后几何回归、视口全程 ready、内存不无界增长、窗口态真的进过"最小化"。
- 诚实性声明维持 §2.2：**不含**引擎 GL 资源释放面；"无悬空纹理"那半句归 LF-03
  （进程内尺寸重建 ×100 验内存不无界增长）。

**本轮最贵的教训**（全文见 `TRAPS.md` 陷阱 102 组）：判据第一版把步进结构的时序写反
（`delayAfter` 语义），采样读的是"0ms 后的世界"却当成"260ms 后的世界"在解释，
制造出一整套互相"矛盾"的读数，烧了 6 轮仪器迭代。**治法是把字段改名成 `waitBefore`，
让这类错误在语法上不可能重犯。**

**已知残余（先记，免得漏）**：
1. 判据**不含**引擎 GL 资源泄漏面（§2.2 诚实性声明）。
2. P-LIF-04 的"鸿蒙真机前后台"一半**归 A7**，本任务只覆盖桌面最小化/恢复。
3. DPR 切换 ×100 未单独成组：判据面与尺寸切换同源（`geometryChange` 都走尺寸变化），
   **共用证据** —— 陷阱 22 要求明示：本组主张的命题是"尺寸世代切换"，DPR 的
   "帧尺寸世代"（`sizeGeneration`）真源在**帧**侧，替身生产者出图尺寸固定 ⇒
   本组**验不到** DPR 语义，那半句移交 A7/Windows 复验（W-T44）。
4. `kMemBudgetMiB = 32` 的余量是按 4 轮实测（峰值 15）定的 2×；Windows 侧内存口径
   不同（无 `phys_footprint`），W-T44 需另定口径。
5. `LF-02b`/`LF-04c` 的零推进容差（≤1）依赖"恢复动画阻塞事件循环"这一实测行为
   （Q3 582ms）；若 Windows 侧不阻塞，零轮应归零 —— W-T44 复验时若出现**成片**零轮，
   先查收敛期而不是判产品。
6. 收口 ×100（`A6_LIF_N=100`）与 LIFECHECK ×2 在 **T47 全量收口**时跑；本轮为
   冒烟档（×20 / ×1）。
