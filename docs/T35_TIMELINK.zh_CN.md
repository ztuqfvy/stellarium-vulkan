## 1 T27 到底留下了什么

`docs/T27_MOUSE_NAV_UI_CHECK.zh_CN.md` §4 与 `docs/evidence/2026-09-29-t27-mouse-nav/README.md`：

> 帧泵推进量（1.5 天/秒）与 `getTimeRate()`（=10）**不一致**。若这是设计（帧推进走固定
> 步长，rate 只管别的语义）则需在产品文档说明；若不是，则是一个独立的时间链路缺陷
> ——**建议单独立项核查**（不在本轮偷偷改）。

README 里那句算术是：`simJD 差 0.61 天 vs rate=10 该走的 4.6e-5 天，**差 4 个数量级**`。

## 2 方法：把它当**测量问题**，而不是"代码里找 bug"

T27 的结论链里有**三个量**：ΔJD、**真实墙钟窗口**、rate 读数。
脱钩 = `ΔJD ≠ 窗口 × rate × scale`。要下这个结论，三个量**必须在同一时刻量齐**。

T27 没做到：ΔJD 与 rate 是 DIAG 读数（不同相位、不同来源），
"400ms" 是**相位名义 delay**（从未与 ΔJD 同刻测过），而 `engineRate` 又是**套件自己改过**的移动靶。

本轮的两件仪器都按"同刻量齐"设计：

| 仪器 | 环境变量 | 做什么 |
|---|---|---|
| 探针 `TIMELINKPROBE` | `STELQUICK_TIMELINK_PROBE=1` | 只报读数、**不打 PASS**（分类靠读数不靠猜）；Q1..Q6d 九问 |
| 判据 `TIMELINKCHECK` | `STELQUICK_TIMELINK_CHECK=1` | **7 条**判据 TL-01..TL-07（§5） |

两条**采样口径**（都承重）：

1. **同一时刻量齐**：ΔJD / 墙钟 / rate / scale / 恒星时 / AltAz 取样在**同一个** `body()` 里
   连续完成（帧泵是 GUI 线程 `QTimer` ⇒ 执行期间不可能重入，无需加锁）。
2. **墙钟走自己的 `QElapsedTimer`**：与帧泵内部那只（`LiveSkyRuntime::m_simClock`）
   **不同实例、不同代码路径** ⇒ 不是自洽假绿（"对照量必须换来源"）。

## 3 定性：三处口径可独立致错，逐一定位

### 3.1 单位误读（`getTimeRate()` 的单位是 **JDay/sec**，不是"实时倍率"）

`src/core/StelCore.hpp:595`：

```cpp
double getTimeRate() const;
//! Get time speed in JDay/sec
```

⇒ rate=10 的含义是 **10 天/（真实）秒**，不是"10 倍实时"。README 的
`10 × JD_SECOND × 0.4s = 4.6e-5 天` 把它当成"× 实时倍率"，**凭空引入 1/86400 因子**，
于是得到了一个"该走的量"，再把真实推进量（0.61 天）除以它 ⇒ "差 4 个数量级"。

### 3.2 `engineRate` 在套件内是**移动靶**（套件自己改的）

`INTERACTCHECK` 的 **IT-05 自己就注入 L 键** ⇒ 走 `increaseTimeSpeed()`
（`src/core/StelCore.cpp:2298-2306`，阶梯 ×10）⇒ **同一进程里** rate 被测试自己
从相位设计值抬上去。T27 证据 README 里的 `engineRate=10` 就是这么来的。

⇒ "帧泵推进量"与那个 `engineRate` 读数**本来就不是同一个东西**。

### 3.3 "400ms" 是**相位名义 delay**，从没量过真实窗口

"0.61 天 ÷ 0.4s = 1.5 天/秒" 这个 1.5 的**唯一来源**就是这里：**用错窗口**（名义 delay）
+ **读错单位**（3.1）。TL-01 实测把它对上了账：

> 把「0.61 天」除以**任何**一个**真实**的 rate 读数，得到的都是**某个真实窗口长度**
> （÷0.1 = 6.1s、÷0.2 = 3.06s、÷1 = 0.61s）——而「1.5 天/秒」只能由「0.61 天 ÷ 名义 0.4s」得到：
> 它**既不是任何时刻的 rate 读数，也不是任何速率的物理量**，是"用错窗口 + 读错单位"的商。

### 3.4 反命题（实测）

TL-01 同刻量齐三个量：**W=3.0596s、rate=0.2、ΔJD=0.617600 天** ⇒ 相对偏差 **0.93%**
（5 跑范围 **0.19%..1.40%**；这条偏差的来历见 §7.1 的注）。
TL-07（恒星时**绝对腿**）：ΔLST=+76.3846° vs ΔJD×360.9856°=+76.3846°，残差 **+0.0000°**。

### 3.5 顺带定性的第二件事：视线**确实**随 JD 转（T27 的机理描述是对的）

T27 说"视线锁地平 ⇒ J2000 视线随 JD 转 ⇒ 自然漂移"，**机理是对的**，错的只是速率读数。
本轮探针 Q6d 实测：静置（无键/无拖拽、`tracking=false`、AltAz 挂载）时
`getViewDirectionJ2000` 的 **ΔRA=34.7580°**（与 ΔLST 同阶）⇒ 视线确实随 JD 转。

真机理在 `updateVisionVector` 的 **"Vision vector locked to its position in the mountFrame"**
分支（`flagLockEquPos` 默认 false）：每帧由 `mountFrameToJ2000(viewDirectionMountFrame)`
重算，而**量天系不动** ⇒ J2000 视线以恒星时速率旋转。

> ⚠️ 这条是**先做静态分析、被实测打脸后改口**的：初版探针按 `panView` 的双零早退断言
> "视线不会自己转"，Q6d 实测 34.76° 直接推翻。**静态分析不能替代读数。**

## 6 🔴 TL-04 的带宽下界为什么是 **0.4** 而不是 0.5

第一轮定稿时 TL-04 写的是 `ratio ∈ [0.5, 1.6]`，负控 A 的红项在 **6/7 与 5/7 之间漂**：
A 把链路砍半 ⇒ 该窗口比值恰好 **≈0.5（实测 0.4990 ↔ 0.5002）**，**正好压在下界上**。
B 的"链路 rate 钉死"在这个窗口同样是 0.5 量级的半速签名。

⇒ 三条腿的职责被搅在一起，且判据红/绿由计时噪声决定。处置：

1. TL-04 的下界改 **0.4**，语义改写为"**冻结必须真零 + 不许补**"——低于 1 的比值是
   TL-01/02/03 的职责（链路整体缩放），TL-04 不重复裁判。
2. TL-04 的相位里**显式**把 rate 钉成 0.2（在此之前它会**继承 TL-03 遗留的 0.4**，
   使 A/B 下的比值随"上一条判据留下的状态"变化 ⇒ 隐式依赖）。
3. 补负控 C 专门咬 TL-04 的真实判别量。

## 8 本轮新血泪（6 条，全是仪器面）

### 8.1 🔴 Qt `.arg()` 与 printf 风格混用 ⇒ **静默失效**

`QString::arg` 只认 `%1`。字符串里写 `%.4f`（从别的 code base 带过来的习惯）
**不报错、原样返回** ⇒ 日志打出一串 `%.4f`。本轮的探针与判据**首跑全线踩中**。
⇒ 脚本自证门：全量日志 `%1` / `%.` 命中必须为 **0**。

### 8.2 🔴 macOS awk 里 **`exp` 是内建函数名**，不能当变量

`awk 'BEGIN { exp = d * 360.9856 ... }'` ⇒ `awk: syntax error … illegal statement`，
**零输出、rc=2**。脚本的 TL-07 复算门因此**静默变成空字符串**——看起来像"没输出"，
而不是"算错了"。⇒ 只用 `expected` 这类非内建名（另有 `log/sqrt/length/substr` 同款）。

### 8.3 🔴 负控的**落点**和**形状**一样重要

第一版负控 C 是"解冻后把冻结期一次性补回来"（形状完全正确、且是真实缺陷形态），
但实测**判据照绿（比值 0.9947）**：解冻后检查还要等 300ms 才 `arm()`，
**"补"的那一脚落在开窗之前**。⇒ 换成"冻结漏推进"（没有落点问题）。
**负控不红 ≠ 判据没牙，也可能是负控没打在测量窗里。**

### 8.4 🔴 就绪门太紧 ⇒ **假红**（与 T22 同源，代价同假绿）

批次连跑 11 套件时，`regression-replaycheck` 出现 **RP-04 假红**（读数 `207×0`），
而**同一命令单独复跑两次都 11/11**。布局就绪门原为 25×100ms = 2.5s，批次下 polish 滞后超过它。
⇒ 按 T22 先例把**就绪门**放宽到 **60×100ms = 6s**（`kUiLayoutWaitTries`），
**断言本身不动**：布局真坏了 6s 后照样判红，门仍有牙。
**假红与假绿一样有害**——都会侵蚀判据的可信度。

### 8.5 🔴 断言里不许塞**受调度影响**的量（TL-02 的假红）

TL-02 初版 = "ΔJD 之比 ≈4" **再加**一条"两窗长度差 ≤20%"的护栏。定稿轮第 2 跑**假红**：

```
TL-02 档A（rate=0.2）：W=2.1907s ΔJD=0.382400；档B（rate=0.8）：W=1.5138s ΔJD=1.214400
                      两窗口长度差=30.9%
✗ TL-02 …ΔJD 之比=3.1757 ∧ 窗口长度差 30.9%（≤20%）⇒ FAIL
```

档A 的窗口**名义 1.5s 被拖到 2.19s**（超 46%）——纯调度抖动。而且抖动期间事件循环被饿住、
**帧泵同源停摆** ⇒ ΔJD 也不涨 ⇒ 裸比值必然偏。**两个量一起被同一个抖动污染**，
护栏和断言一起翻车。

处置：TL-02 改成**速率归一化**比较 `(ΔJD_B/W_B)/(ΔJD_A/W_A)` —— 对"窗口长度不等"在**解析上**免疫；
"窗口长度差"**降为读数**（它已由归一化消掉，留着当断言只会把调度抖动误记成产品回归）。
同一跑里 TL-03 用的是**比值之比**，天然免疫，照绿（3.0061 vs 3.0044）。

> **通则**：判据里出现的每一个量，都要问一句"**它会不会被环境（调度/负载）单独改变**"。
> 会 —— 就不能把它当断言，要么换等比形式，要么降为读数。

### 8.6 🔴 治本：给"窗口型"读数加**有界就绪门**

§8.5 只是消掉了 TL-02 的那一条；**根因是共用的**：本套判据全都用
`QTimer::singleShot(delayAfter)` 划窗，一旦事件循环被饿住（批次连跑 11 套件 / Spotlight /
上一个进程的 Metal 拆卸），**定时器与帧泵同源停摆** —— 窗口被拖长、ΔJD 又少涨，
**两个量被同一个抖动污染** ⇒ 该窗对"链路是否自洽"**没有分辨力**。

处置（沿 T22/T27/T28/T33「有界就绪门」先例，**仪器没接上 ⇒ 重测，不判红**）：
`take()` 里加一道门 —— **W 超名义值 25% ⇒ 本窗不可判 ⇒ 重起窗、把本步原样重跑**
（单窗预算 **3** 次；判据代码里 `if (r.suspect) return;` 就是短路点）。

两条性质让这道门**不会掩护真缺陷**：

1. 门是**单边**的：`singleShot` 只会晚不会早 ⇒ `W < 名义` 不可能；
2. **真缺陷不改墙钟**：链路半速 / rate 钉死都不改变窗口的墙钟长度。

预算耗尽后仍按现状判定，并在日志里写明"读数可能受环境污染"（**不洗成 PASS**）。
当 11 个窗口都过门时，日志里**一条** `窗口就绪门：` 行都不该出现——脚本据此可判断本批是否干净。
